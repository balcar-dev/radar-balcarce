1. La idea en una imagen

Pensalo como un diario impreso que se imprime solo, cada media hora. Nadie lo arma mientras vos lo leés: ya está listo, y solo hay que repartir copias.

El taller · GitHub

Donde se fabrica

Un empleado automático (un “robot con reloj”) lee las noticias, las junta, las evalúa, las escribe con IA y arma todas las páginas del diario.

La vidriera · Cloudflare

Donde se entrega

Guarda las páginas ya hechas y las reparte rápido a cada lector. No piensa, no escribe: solo entrega copias.

Por qué importa: como las páginas ya están hechas cuando alguien entra, el sitio es muy rápido y casi no cuesta. Y como el taller trabaja solo, funciona con la computadora de ustedes apagada.

2. Las palabras, traducidas

Estas son las que van a aparecer cuando hablemos de mejoras. Cada una con una comparación.

Repositorio (“repo”)
Una carpeta en internet con todo el proyecto y el historial de cada cambio. Es como un Drive que recuerda quién cambió qué y cuándo. Ahora es público: cualquiera puede mirarlo (no las claves, que se guardan aparte).
GitHub
La empresa que aloja ese repositorio. Es el “depósito” del proyecto.
GitHub Actions / workflow
Los empleados automáticos de GitHub. Un workflow es una receta que un robot repite: “cada media hora, hacé esto”. Hoy hay 22 recetas.
Cron
El despertador. Dice “a tal hora, arrancá”. Hoy lo maneja un servicio aparte, cron-job.org, que toca el timbre de GitHub.
Feed (RSS)
La lista de las últimas noticias que un medio ofrece en formato para máquinas. Es la ventanilla por donde se las lee.
JSON
Una planilla en texto. Acá guardan todo en archivos así: las noticias, las decisiones, las correcciones.
IA / Gemini / Groq
Los redactores automáticos. Gemini (de Google) escribe las notas y las voces; Groq es el suplente para leer.
Next.js
La imprenta: toma las planillas (JSON) y las convierte en páginas web.
Compilar (“build”)
El momento en que la imprenta arma las más de mil páginas.
HTML estático
Páginas ya impresas. Lo contrario es una página “dinámica”, que se cocina en el momento de entrar y necesita un servidor trabajando.
Cloudflare Pages
El servicio que guarda las páginas impresas y las reparte por el mundo. Es la vidriera.
Worker
Un empleado mínimo de Cloudflare: un programa chico que responde al instante o se despierta a una hora fija.
Secreto / clave
Una contraseña que usan los robots (Gemini, Meta, etc.). Se guarda en una caja fuerte de GitHub y nunca va escrita en el proyecto.

3. El recorrido de una noticia

Tocá cada paso para ver qué pasa adentro. Todo esto corre solo, cada 30 minutos.

  1. Se leen las fuentesUnos 90 medios, más de 200 feeds

    robotCada media hora se visita cada ventanilla (feed) y se baja la lista de notas. Se anota la fecha de cada una y se descartan las que no sirven de entrada (otro país, policiales de afuera, etc.).

    Si una fuente se cae o viene vacía, no da error: simplemente trae menos. Por eso el sistema deja un aviso amarillo.

  2. Se juntan las que cuentan lo mismoEl “cruce” de medios

    robotSi cinco medios cuentan el mismo hecho, se arma una sola historia con cinco fuentes. El sistema recuerda lo de las últimas 36 horas para no repetir.

    Una noticia de afuera solo pasa si la cuentan varios medios (entre 2 y 4 según la sección). Lo de Balcarce pasa con menos.

  3. Se clasifica y se puntúaSección, puntaje y semáforo

    robotSe decide la sección (de las 11), qué tan importante es (puntaje) y el semáforo: verde sale sola, amarillo espera a una persona, rojo no sale (por ejemplo, riesgo de identificar a un menor o a una víctima).

    Lo local pesa más: las fuentes de Balcarce suman 24 a 30 puntos y las nacionales 8.

  4. Una IA la lee y opinaLectura con IA

    IALee cada nota nueva y decide: ¿es de acá?, ¿es la sección correcta?, ¿hay que sacarla? Solo puede frenar o corregir; nunca destraba algo que el semáforo bloqueó.

  5. Otra IA escribe la notaRedacción

    IACon el texto completo de la fuente y el criterio editorial, Gemini escribe título, bajada y cuerpo. Cada nota dice quién la escribió.

  6. Se verifica lo escritoControl contra la fuente

    robotCada dato (nombres, cifras, fechas) se compara con lo que dicen las fuentes. Si algo no cierra, se corrige sin inventar o la nota no sale. Una nota sin cuerpo de al menos 70 palabras no se publica.

  7. Se ponen las decisiones de ustedesPanel del celular

    personasLo que Hernán y Andrés decidieron desde el celular (publicar, retirar, corregir) manda sobre lo automático. Política y Policiales esperan siempre a una persona en las redes.

  8. Se guardan las planillasArchivos web/data/*.json

    robotTodo lo decidido queda escrito en archivos JSON dentro del repositorio. Eso es “la base de datos”: no hay otra.

  9. Se imprime el diarioCompilar con Next.js

    robotNext.js lee las planillas y arma las páginas: la portada, una por cada nota, las secciones, el buscador, el mapa del sitio para Google. Hoy son 1.148 páginas.

  10. Se reparteCloudflare Pages

    robotLas páginas se suben a Cloudflare y quedan en su red de copias. Cuando alguien entra, recibe la copia más cercana. Después, otros robots arman las piezas de Facebook e Instagram y un vigilante controla que todo funcione.

Un dato clave del diseño: las decisiones y las notas viven dentro del repositorio de GitHub (pasos 7 y 8). GitHub es a la vez la bodega y el taller. Por eso, si GitHub o su cola de robots se traba, el diario deja de actualizarse (ya pasó dos veces, una de 3,5 horas y otra de 10).

4. Cómo elige el sistema qué publicar

No es una sola decisión: son tres capas que se miran en este orden. Importa distinguirlas porque cada una hace algo distinto.

Capa 1 · Semáforo

¿Puede salir?

Mira el título y el comienzo del texto, y se queda con lo primero que encuentra. Es la capa que protege.

Rojo: no sale
  • Temas sensibles (menores de edad, abuso, violación, femicidio, suicidio, trata).
  • Lo que nunca se publica (listas de sepelios).
Amarillo: espera a una persona
  • Palabras como denuncia, detenido, imputado, víctima, niño, adolescente.
  • Cotización del dólar (ya se muestra en /dolar), política internacional sin relación con Balcarce, y avisos de sorteos o promociones.
  • Algo de afuera que cuentan pocos medios.
Verde: sale sola
  • Un comunicado oficial, o una nota que ninguna regla frenó.

La lista roja es una decisión editorial y de seguridad: no se toca sin hablarlo.

Capa 2 · Lectura con IA

¿De verdad es de acá y vale la pena?

Una IA lee cada nota nueva y completa una ficha con valores cerrados (no escribe libre): el ámbito (Balcarce, región, provincia, nacional, internacional), la sección, el impacto en Balcarce (directo, indirecto, nulo), la importancia, y si es publicidad o chimento.

Regla de oro: la IA solo puede endurecer. Puede sacar una nota o mandarla a esperar, pero nunca destrabar algo que el semáforo frenó.

Ejemplos reales de la corrida de las 22:30 del 7/10, en la que leyó 14 notas nuevas:

FUERA “Zaira Nara y Jakob Von Plessen volvieron a apostar al amor” (es un chimento)

FUERA “Tragedia en Mendoza: hallaron muerto a un niño de 12 años…” (policial que no es de Balcarce)

REPETIDA “Campo de Pato campeón del Regional Sub-16 de Hockey” (se junta con otra que cuenta lo mismo)

Límite de uso: de a 12 notas por pedido, hasta 5 pedidos por corrida y 200 por día con su clave propia. Si Gemini no responde, lo reemplaza Groq.

Capa 3 · Puntaje

¿Qué va primero?

Un número de 0 a 100 que solo ordena: qué ocupa la tapa, qué entra en el cupo y qué va a Facebook y a los podcasts. No decide si la nota sale. Suma puntos así:

Es de Balcarce+25
Muy reciente (menos de 3 h)+25
Un medio de afuera dice “Balcarce” en el título+22
Nombra a una figura argentina+16
Cada medio más que lo cuenta (hasta 4)+10 c/u, tope +40
Peso del medio de origen24 a 30 si es local · 8 si es nacional
Automovilismo+8
Trae foto / texto completo+6 / +4

Por eso lo local gana casi siempre: un medio de Balcarce arranca con 24 a 30 y suma 25 más por ser de acá, contra 8 de un medio nacional.

En una frase: el semáforo dice si puede salir, la IA dice si de verdad corresponde y el puntaje dice cuánto lugar merece. Después vienen los ocho controles finales (más abajo), y recién ahí se publica.

5. Los “8 pasos”: por qué ocho

Antes de publicar cada nota, el sistema la hace pasar por ocho controles, siempre en este orden. Si falla uno, no sale.

  1. ¿La retiraron a mano? Si sí, no sale.
  2. ¿Qué decidió una persona? Si alguien decidió, manda eso. Si no, el semáforo.
  3. ¿Llega tarde? Una noticia vieja que nunca salió no se estrena (más de 12 horas).
  4. ¿Qué texto lleva? El de la persona, si no el de la IA, si no el resumen de la fuente.
  5. ¿Qué dirección tiene? Se fija la primera vez y no cambia nunca más.
  6. ¿Hay correcciones? Pisan título, bajada, sección o cuerpo.
  7. ¿Es algo que nunca se publica? Por ejemplo, listas de sepelios, aunque alguien las haya aprobado.
  8. ¿Tiene cuerpo? Sin cuerpo de 70 palabras o más no se publica.
¿Por qué ocho y no más o menos? No hay un motivo matemático. Cada control cubre una forma distinta de que algo salga mal: una persona que se arrepiente (1, 2, 6), el tiempo (3), el texto (4, 8), los enlaces (5) y lo que jamás debe salir (7). Lo que sé por cómo está escrito el proyecto: cada vez que algo salió mal publicado, se sumó una prueba y una regla. Es decir, la lista creció por experiencia. Ocho no es el número ideal: es el que quedó.

Una conclusión práctica: si quieren simplificar, no hay que contar pasos, hay que agrupar por riesgo. Por ejemplo, 1, 2 y 6 son “lo que decide una persona” y podrían ser un solo bloque.

7. ¿Por qué tarda unos 7 minutos? ¿Es mucho?

Miré una corrida real, la de las 22:30 del 7/10, y cronometré cada tramo con los registros de GitHub. Desde que arranca hasta que la nota queda en la web pasaron 6 minutos 58 segundos. Hay dos robots seguidos: el primero junta y escribe, el segundo imprime y publica.

Robot 1 · Actualizar la web (4 min 11 s)
Preparar y probar el código27 s
Leer unas 200 fuentes31 s
La IA lee y clasifica14 s
La IA escribe las notas57 s
Buscar fotos50 s
Imprimir el diario (1ª vez)66 s
Robot 2 · Cloudflare Pages (2 min 36 s)
Esperar y preparar16 s
Imprimir el diario (2ª vez)111 s
Subir a Cloudflare29 s

Las barras naranjas son el mismo trabajo hecho dos veces. “Buscar fotos” es una estimación: el registro no marca el comienzo de ese tramo, solo cuándo termina (50 s para 2 notas nuevas).

¿Es mucho o poco? Para lo que hace, poco: leer 200 fuentes, juntar unas 700 historias, hacer leer y escribir a una IA, verificar y armar más de 1.400 páginas en 7 minutos es rápido. Lo que sí pesa más es el ciclo: una noticia que sale a las :01 espera hasta 30 minutos a que arranque la próxima vuelta, así que la demora real para un lector es de unos 22 minutos en promedio (15 de espera más 7 de proceso). Los 7 minutos son un tercio de eso.

Dónde está lo que se puede ahorrar

  • Imprimir dos veces (177 s, el 42% del tiempo). El primer robot arma el sitio como control y el segundo lo vuelve a armar para publicar. Si se publica lo que ya se armó una vez, se ahorran unos 2 minutos. Es la mejora más grande y no cuesta nada.
  • Sin memoria de impresión. El registro avisa “No build cache found”: cada vez se empieza de cero. Guardar esa memoria es gratis y debería acortar algo ambas impresiones; cuánto, no lo sé sin probarlo.
  • Fotos: 50 segundos para 2 notas es mucho. Conviene mirar qué hace ese tramo, porque probablemente espera en fila.
  • Las pruebas no son el problema: 1.840 pruebas tardan solo 16 segundos. Corrijo lo que dije antes: su costo es de tiempo bajo; el riesgo es que una prueba mal escrita frene todo.
Otro hallazgo, de contenido más que de velocidad: en esa corrida fallaron unas 50 fuentes de las ~200 (“fetch failed”), entre ellas La Nación, Clarín, TN, Perfil, ESPN, iProfesional y también Puntonueve, que es de Balcarce. No sé si son siempre las mismas: hay que mirar varias corridas. Muchos sitios bloquean las visitas desde los servidores de GitHub. Si se repite, el sistema está perdiendo cobertura sin que se note, porque una fuente caída no da error, solo trae menos.
¿Armamos un proceso engorroso? Tiene muchos pasos, pero casi todos tienen una razón concreta (cada uno nació de algo que salió mal) y la velocidad no es el síntoma. Lo engorroso está en otro lado: 22 recetas de robots, 1.840 pruebas, el repositorio usado como base de datos con 48 commits por día. Eso no hace lento al sitio; hace más difícil cambiar cosas sin romper otras. Por eso la prioridad no es acelerar, es simplificar y vigilar.

10. Qué no conviene (y por qué)

Firebase

Pide tarjeta para ejecutar tareas programadas y no resuelve nada que Cloudflare no resuelva. Sumaría otro proveedor.

ElevenLabs

El plan gratis no alcanza para 6 a 8 audios por día y no deja usar las voces comercialmente. Rompe además la regla de no cambiar de voz.

Pasar todo a privado en GitHub

Hoy son unos 11.500 minutos de robot por mes; el plan privado incluye 2.000 a 3.000. El exceso saldría unos US$ 55 a 60 por mes solo para la actualización de la web.
